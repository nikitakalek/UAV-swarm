# Определение, таксономия задачи и требования

Документ отвечает на шаги 1–3 из раздела 40 master prompt:
что мы называем роем, где он даёт выигрыш, и какие требования мы к нему предъявляем.

---

## 1. Что мы называем «роем» — строгое определение

В литературе термин «рой» (swarm) используется в трёх разных смыслах, и путаница между
ними — главный источник нечётких проектов. Разведём их.

| Уровень | Название | Признаки | Примеры |
|---|---|---|---|
| L1 | **Роевой интеллект (swarm intelligence, в строгом смысле)** | сотни–тысячи агентов; анонимные, взаимозаменяемые агенты; только локальные правила; нет глобального состояния и глобального плана; поведение *эмерджентное*; масштабируемость без изменения правил | стаи птиц, Kilobot, perceptron-рои, формации Crazyswarm (частично) |
| L2 | **Распределённая мультироботная система / скоординированная команда** | десятки агентов; агенты гетерогенны и идентифицируемы; есть явный механизм распределения задач; локальная координация + обмен намерениями; допускается лидер или наземная станция как один из узлов | ваша задача, команды на CBBA, MRS UAV System |
| L3 | **Управление парком дронов (fleet management)** | оператор управляет группой; задачи назначаются и перераспределяются, но автономность агента низкая; вся логика в центре | DJI FlightHub, UgCS, большинство коммерческих «дрон-в-коробке» |

**Где находится SwarmCore:** между L2 и L3, и это нужно признать открыто.

**Плохая новость:** честное позиционирование «мы делаем систему уровня L2, а не L1»
звучит слабее, чем «мы делаем рой».
**Хорошая новость:** реальные рои уровня L1 бесполезны для ваших прикладных задач — они
не поддерживают сложные гетерогенные задачи, не дают гарантий, не проходят по регуляторике.
L2 — это то, что реально нужно и что реально можно построить и защитить.

**Правильная формулировка для защиты:**

> SwarmCore — распределённая система управления группой БПЛА, в которой миссия
> декомпозируется в множество задач, задачи динамически распределяются между агентами
> по аукционному/консенсусному протоколу, а выполнение миссии устойчиво к отказам
> агентов и деградации канала связи. В отличие от платформ управления парком дронов,
> ключевые решения принимаются не только в центре: агент располагает полной копией
> состояния миссии и способен продолжать и ремонтировать назначение при потере связи
> с центром.

## 2. Формальная постановка задачи и таксономия

### 2.1. Таксономия (Gerkey & Matarić 2004; Korsah et al. 2013 «iTax»)

Любая задача многоагентного распределения описывается тремя осями:

**Ось 1 — роботы:**
- `ST` (single-task robots): агент выполняет не более одной задачи одновременно
- `MT` (multi-task robots): агент может выполнять несколько задач параллельно

**Ось 2 — задачи:**
- `SR` (single-robot tasks): задача требует одного агента
- `MR` (multi-robot tasks): задача требует коалиции агентов

**Ось 3 — назначение:**
- `IA` (instantaneous assignment): назначение «сейчас», без планирования на будущее
- `TA` (time-extended assignment): назначение с учётом расписания и будущих задач

**Классификация SwarmCore:**

| Подзадача | Класс | Следствие |
|---|---|---|
| Покрытие ячейки / обследование сектора | `ST-SR-TA` | стандартная mTSP с энергией → CBBA, маршрутизация в OR-Tools |
| Обнаружение цели + удержание наблюдения | `ST-SR-IA` | аукцион в реальном времени |
| Одновременное взятие цели несколькими БПЛА (триангуляция, подъём груза) | `MT-MR-TA` | **существенно сложнее**: формирование коалиций, гиперграфовые назначения, CBBA с коалициями |
| Инспекция объекта с нескольких ракурсов | `ST-MR-TA` | требуется синхронизация по времени |

**Практический вывод:** начинать нужно со `ST-SR-TA`. Это уже нетривиально (маршрутизация
с энергией), но для этого класса есть зрелые алгоритмы. `MR`-задачи (требующие коалиции)
не включать в MVP — там комбинаторика взрывается, и вы не успеете.

### 2.2. Формальная модель

**Агенты.** `A = {1..N}`, агент `i` описывается состоянием
`s_i = (p_i, v_i, ψ_i, e_i, h_i, σ_i)`, где `p` — позиция, `v` — скорость, `ψ` — курс,
`e` — остаток энергии, `h` — исправность (health), `σ` — вектор доступности сенсоров.

**Задачи.** `T = {1..M}`, задача `j` описывается
`τ_j = (loc_j, type_j, req_j, dur_j, priority_j, tw_j)`, где `loc` — местоположение или
область, `req` — требования к сенсору, `dur` — ожидаемая длительность, `tw` — временное окно.

**Время выполнения.** Ключевая величина — время на задачу (time-on-task) для пары (агент, задача):
```
t_ij = travel_time(p_i, loc_j) + service_time(τ_j)
travel_time = ||p_i − loc_j|| / v_cruise
service_time(τ_j) = area_j / (v_sweep · w_sweep)     # для задач покрытия
service_time(τ_j) = |views_j| · t_per_view + t_reposition   # для инспекции
```

**Энергия.** Для последовательности задач `seq_i = (j_1, j_2, ..., j_k)`, назначенной
агенту `i`:
```
E_i(seq_i) = Σ_m [ E_travel(p_{j_m} → p_{j_{m+1}}) + E_service(τ_{j_m}) ] + E_return(p_{j_k} → home)
```
Ограничение: `E_i(seq_i) ≤ e_i · (1 − reserve)`, `reserve ≈ 0.2` (обязательный резерв
на возврат и ветер). Это ограничение дальности, которое делает задачу похожей на VRP
с ограничением пробега, а не на задачу назначения.

**Критерий оптимальности (обобщённый).** Для миссии `M`:
```
maximize  U(M) = Σ_j priority_j · 1[τ_j выполнена вовремя]
          − λ_E · Σ_i E_i  − λ_T · makespan
```
где `makespan` — общее время миссии (момент завершения последней задачи). Или, для
поисковой миссии с неопределённостью:
```
maximize  E[число обнаруженных целей к моменту T_deadline]  − λ_E · Σ E_i
```

**Назначение.** `x_ij ∈ {0,1}`, при этом `Σ_j x_ij` не ограничено единицей (агент берёт
маршрут из нескольких задач) — это и есть выход за пределы задачи назначения
(assignment problem).

### 2.3. Что здесь принципиально стохастично (и нельзя притворяться, что нет)

1. Позиция цели неизвестна → задача поиска = **POMDP** по своей природе, а не задача
   покрытия. Практическое упрощение: детерминированный планировщик покрытия + байесовское
   обновление карты вероятности. Это стандартный компромисс, но его нужно назвать явно.
2. Время выполнения задачи неизвестно (шум, ветер) → стохастическая длительность.
3. Обнаружение цели вероятностно → `Pd < 1`, возможны пропуски, требуется повторный проход.
4. Отказы и потери связи случайны.

**Следствие для планирования:** план, построенный как детерминированное расписание,
будет ломаться на первом же отклонении. Поэтому нужен механизм ремонта (перераспределение
/ перепланирование) и явный бюджет на него — это и есть центральная часть вашего проекта.

## 3. Где рой реально даёт выигрыш (и где нет)

Нужно уметь отвечать на вопрос «а зачем вообще несколько дронов» числами, а не интуицией.

### 3.1. Три режима, где преимущество существует

**Режим 1. Параллельное покрытие большой площади.**
Теоретическая оценка: при независимом разбиении площади `A` на `N` равных частей время
покрытия
```
T(N) ≈ A / (N · v · w)  + c(N)
```
где `w` — ширина полосы обзора, `c(N)` — накладные расходы координации (растут с N).
**Важное следствие:** выигрыш суб-линеен, и существует `N*`, после которого `c(N)`
съедает выигрыш. **Эта точка `N*` — один из ваших измеримых результатов.** Для
акселератора это сильное утверждение: «мы знаем, сколько дронов имеет смысл запускать
на такую территорию, и почему».

**Режим 2. Отказоустойчивость.**
Модель: агенты отказывают с интенсивностью `λ` (экспоненциальное распределение времени
до отказа). Доля потерянной работы за миссию:
```
ожидаемая потеря ≈ 1 − exp(−λ · N · T_mission)
```
Без перераспределения потеря задач = доля отказавших агентов. С перераспределением потери
близки к `0` при условии, что избыточная ёмкость группы `> 0`. **Выигрыш роя здесь не в
скорости, а в вероятности выполнения миссии.** Это самая защищаемая часть концепции — но
её надо измерять как `P(mission complete)` и `T_recovery`, а не как «время миссии».

**Режим 3. Нестационарность (появление новых целей).**
Ключевой параметр — не число целей, а **отношение характерного времени перераспределения
к характерному времени изменения обстановки** `T_realloc / T_change`. Если оно мало —
динамика имеет смысл; если велико — вы не успеваете и статический план не хуже.
Это ещё один измеримый количественный результат.

### 3.2. Где преимущества НЕТ (и это нужно честно сказать)

- Площадь мала, и один БПЛА покрывает её за приемлемое время → координация только добавляет
  накладные расходы и риск столкновений.
- Задача не параллелизуется (одна цель, требующая одного сенсора).
- Требуется жёсткая синхронизация (например, когерентная радиолокация) — это другой класс
  задач, требующий субмикросекундной синхронизации, недостижимой на вашем стеке.
- Плотность целей очень низкая и распределена неоднородно: если одна «горячая» ячейка
  содержит 90 % целей, `N` дронов в ней мешают друг другу, а не помогают.

**Условия, при которых ваш проект выглядит сильно:** большая территория, неоднородная
плотность целей, ненулевая вероятность отказов, ограниченный канал связи, требование
продолжить миссию при потере центра. Все четыре условия нужно **явно проговорить в
презентации как область применимости**, а не как «наш рой хорош всегда».

## 4. Системные требования

### 4.1. Функциональные

| ID | Требование | Проверяется |
|---|---|---|
| FR-1 | Приём миссии высокого уровня (плагин + параметры) | тест: 2 разных типа миссии на одном ядре |
| FR-2 | Декомпозиция миссии в набор задач с географической привязкой | число и корректность задач для заданной области |
| FR-3 | Распределение задач между агентами с учётом энергии, позиции, сенсоров, приоритета | сравнение с оракулом-оптимумом |
| FR-4 | Планирование маршрута агента по его набору задач с ограничением энергии и возвратом домой | валидатор: `E_i ≤ e_i·(1−reserve)` |
| FR-5 | Предотвращение конфликтов (стратегическое + тактическое) | 0 столкновений, число опасных сближений |
| FR-6 | Обнаружение отказа агента и перераспределение его задач | `T_recovery`, доля завершённых задач |
| FR-7 | Обнаружение потери связи и переход в автономный режим | доля миссии, выполнимая без наземной станции (GCS) |
| FR-8 | Восстановление состояния после возврата связи без дублирования задач | проверка согласованности: ни одна задача не выполнена дважды и не потеряна |
| FR-9 | Приём и обработка события «обнаружена новая цель» с приоритетным прерыванием | время реакции, изменение плана |
| FR-10 | Полный журнал событий и воспроизводимость прогона по зерну (seed) + конфигу | побитовое совпадение метрик при повторе |
| FR-11 | Визуализация состояния роя и причин решений (почему переназначили) | наличие журнала объяснений |

FR-8 и FR-11 — те, о которых обычно забывают и которые дают наибольшее впечатление
на инженерной защите.

### 4.2. Нефункциональные (с числами)

| ID | Требование | Значение | Почему такое |
|---|---|---|---|
| NFR-1 | Масштабируемость в симуляции | 50 агентов, ≥ 10× реального времени на 1 ядро | 100+ агентов — цель, но не для MVP |
| NFR-2 | Частота обмена состоянием (локальная координация) | 5 Гц | ниже 5 Гц ORCA/VO теряют работоспособность |
| NFR-3 | Частота обмена намерениями/задачами | 1 Гц | редкие события, экономим канал |
| NFR-4 | Задержка локального канала | ≤ 200 мс, моделируется | граница применимости тактического избегания |
| NFR-5 | Время глобального перераспределения | ≤ 2 с при N=20 | больше — рой не успевает за изменениями |
| NFR-6 | Трафик на агента (базовый режим) | ≤ 5 кбит/с | реалистично для Wi-Fi-сети и допустимо для телеметрии |
| NFR-7 | Бюджет вычислений на агента (борт) | ≤ 30 % одного ядра бортового компьютера | иначе не полетит на реальном железе |
| NFR-8 | Число столкновений | **строго 0**, жёсткое ограничение | безопасность — не метрика качества |
| NFR-9 | Минимальная горизонтальная сепарация (модель) | 5 м | эшелонирование по высоте: ±3 м |
| NFR-10 | Воспроизводимость | детерминизм при фиксированном зерне (seed) | иначе эксперименты недоказуемы |
| NFR-11 | Время работы миссии (модель) | ≤ 15 мин на аккумулятор, резерв 20 % | соответствует реальному квадрокоптеру класса 2–3 кг |
| NFR-12 | Синхронизация времени между агентами | расхождение ≤ 10–50 мс | нужно для корректного слияния данных и логики перераспределения; в симуляции — общий шаг `dt`, на железе — GPS PPS / NTP |

Значения NFR — **предлагаемые стартовые**, их нужно согласовать с командой и с реальным
железом, но они должны быть числами уже сейчас: без чисел требования не проверяемы.

### 4.3. Требования безопасности и человек в контуре управления (обязательный раздел)

| ID | Требование |
|---|---|
| SR-1 | Геозона (бесполётная зона) — жёсткое ограничение планировщика, нарушение запрещено на уровне валидатора плана |
| SR-2 | При потере GPS — переход в режим удержания/возврата, не продолжение миссии |
| SR-3 | Оператор имеет право на вмешательство: пауза миссии, возврат всех, переназначение конкретной задачи вручную |
| SR-4 | «Чёрный ящик»: журнал команд и решений, пригодный для разбора инцидента |
| SR-5 | Правило расхождения: если факт отклоняется от плана больше чем на порог, агент не импровизирует, а запрашивает перераспределение (либо, при потере связи, применяет заранее известное безопасное поведение) |
| SR-6 | План считается допустимым только после проверки валидатором: геозоны, энергия, минимальная сепарация, высотный коридор |

SR-6 — недооценённая, но очень сильная вещь: **валидатор плана** превращает «мы надеемся,
что планировщик не ошибается» в «мы гарантируем, что недопустимый план не будет исполнен».
Это дёшево в реализации и заметно повышает инженерный уровень проекта.

## 5. Область применимости (формулировка для презентации)

> SwarmCore предназначен для задач, где группа БПЛА обследует протяжённую территорию с
> неоднородным распределением объектов поиска, в условиях ограниченного канала связи и
> ненулевой вероятности отказа аппаратов, и где требование состоит в том, чтобы миссия
> продолжалась при отказе отдельного аппарата или потере связи с наземной станцией.
> Система не предназначена для задач, требующих жёсткой синхронизации, коалиционного
> выполнения задач одним объектом или работы в плотном городском трафике.
