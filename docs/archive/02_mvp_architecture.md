## 1. Реалистичный MVP: разрезать на 4 этапа

Исходный «предполагаемый MVP» из master prompt (симулятор + 5–10 БПЛА + миссия +
распределение + перераспределение + избегание столкновений + отказы + визуализация) — это
**не MVP, а четыре разных MVP**. Если пытаться сделать всё сразу, получится демо, которое
работает в одном сценарии и не даёт ни одной цифры.

| Этап | Что входит | Что НЕ входит | Контрольная точка (gate, критерий готовности) |
|---|---|---|---|
| **MVP-0: испытательный стенд + базовый метод** | среда 2D, модель БПЛА (кинематика), модель обнаружения, задачи покрытия, статическое разбиение, метрики, прогон без графического интерфейса по конфигу, CSV на выходе | графический интерфейс, отказы, перераспределение, локальная координация, ML | `swarmcore run --scenario X --allocator static_oracle --seed 1` даёт CSV с метриками; повтор даёт те же числа |
| **MVP-1: Динамика** | динамическое перераспределение, отказы агентов, низкая батарея, новые цели, событийный журнал, T_recovery | тактическое избегание, разрыв связи с наземной станцией, PX4 | сценарий с отказом 20 % агентов завершается с ≥ 95 % выполненных задач, `T_recovery ≤ 2 с` |
| **MVP-2: Связь и децентрализация** | модель канала (дальность/задержка/потери/полоса), разделение сети, CBBA как децентрализованный распределитель, режим без наземной станции, согласованность после восстановления | PX4, железо | прогон с полным разрывом связи на 30 % времени миссии: миссия продолжается, после восстановления нет дублированных и потерянных задач |
| **MVP-3: Локальная координация + сравнение архитектур** | тактическое избегание (ORCA или ORCA-подобное), исследование методом исключения (ablation), факторный эксперимент по 4 архитектурам, графики | ML | отчёт с графиками пересечения кривых (crossover) по N, λ_failure, потерям связи; 0 столкновений |

**Это и есть ответ на «шаг 5» и «шаг 9» из раздела 40.** После MVP-2 у вас уже есть
защищаемый научный результат; MVP-3 — усиление.

### 1.1. Что обязательно должно быть в MVP-0 (часто пропускают)

1. **Модель обнаружения.** Без неё все метрики бессмысленны.
2. **Валидатор плана** (геозоны, энергия, сепарация). 20 строк кода, а уровень проекта
   меняет заметно.
3. **Испытательный стенд прогонов (harness)** (матрица конфигураций × зёрен (seed) →
   CSV → графики). Это главный артефакт проекта, а не визуализация.
4. **Детерминизм** (фиксированный `dt`, генератор случайных чисел с фиксированным зерном,
   `run_manifest.json` с хэшем конфига).

### 2.1. Модули и ответственности

| Модуль | Ответственность | Ключевой интерфейс |
|---|---|---|
| `World` | среда: границы, препятствия, бесполётные зоны, карта вероятности целей, цели | `World.step(dt)`, `World.observe(agent, sensor)` |
| `MissionPlugin` | доменная декомпозиция миссии в `TaskSet` | `decompose(mission, world) -> TaskSet` |
| `TaskSet` | список задач + их состояние (unassigned/assigned/in_progress/done/failed) | `tasks[...]`, `unfinished()` |
| `Allocator` | распределение задач (стратегия: статическая / централизованная / CBBA) | `allocate(state, tasks) -> Assignment` |
| `Planner` | маршрут агента по его задачам с учётом энергии | `plan(agent, tasks) -> Trajectory` |
| `PlanValidator` | проверка допустимости плана (геозона, энергия, сепарация) | `validate(plan) -> Ok | Violations` |
| `Agent` | локальный цикл: следование, локальный ремонт, безопасность | `Agent.step(dt, neighbors, tasks)` |
| `CommsBus` | доставка сообщений с дальностью/задержкой/потерями/полосой | `send(src, dst, msg)`, `broadcast(src, msg)` |
| `FaultManager` | инъекция и детекция отказов, потеря связи, низкая батарея | `inject(event, t)`, `detect(state)` |
| `MetricsRecorder` | сбор метрик по шагам и событиям | `record(...) -> rows` |
| `SimLoop` | детерминированный цикл времени | `run(scenario, seed) -> RunResult` |

**Ключевое архитектурное решение:** `Allocator` — это стратегия с единым интерфейсом.
Именно это позволяет поставить главный эксперимент (сравнение архитектур), не переписывая
симулятор. Реализации:
- `StaticOracleAllocator` — офлайн-оптимум, честный базовый метод;
- `CentralizedAllocator` — OR-Tools CP-SAT (малые N) / жадный централизованный (большие N);
- `CBBAConsensusAllocator` — распределённый аукцион, работает без центра;
- `HybridAllocator` — центральное назначение + локальный ремонт агентами.

Второе ключевое решение: `Agent` — абстракция над **источником движения**. В симуляции
за ней стоит кинематическая модель, при интеграции — MAVSDK-обёртка над PX4. Тогда переход
«симуляция → SITL → железо» не требует переписывания логики роя. Это стоит заложить
с самого начала, даже если MAVSDK появится через 3 месяца.

## 3. Математическая модель (минимально достаточная)

### 3.1. Движение агента

**MVP-0 (безмассовая кинематическая модель):** агент летит к текущей путевой точке
с постоянной крейсерской скоростью `v_c`, мгновенно меняет курс. Достаточно для проверки
алгоритмов распределения и покрытия.
```
p_i(t+dt) = p_i(t) + v_c · normalize(wp − p_i(t)) · dt
```

**MVP-2 (двойной интегратор с ограничениями):**
```
ṗ = v,  v̇ = a,  |a| ≤ a_max,  |v| ≤ v_max,  |ψ̇| ≤ ψ̇_max
```
Этого достаточно, чтобы локальное избегание конфликтов имело смысл: без ограничений на
динамику задача избегания тривиальна.

**Чего не делать:** полную 6-DOF модель, аэродинамику, модель моторов. Это не влияет
на выводы о распределении задач и съест весь бюджет времени.

### 3.2. Энергия (мультиротор, модель Zeng et al.)

```
P(v) = P0·(1 + 3v²/U_tip²)                                  # мощность профиля лопастей
     + Pi·( sqrt( sqrt(1 + v⁴/(4·v0⁴)) − v²/(2·v0²) ) )     # индукционная мощность
     + 0.5·d0·ρ·s·A·v³                                      # паразитная мощность
```
где `P0` — мощность профиля лопастей (в висении), `Pi` — индукционная мощность (в висении),
`U_tip` — скорость кончика лопасти, `v0` — индуцированная скорость в висении,
`d0·ρ·s·A` — аэродинамический коэффициент.

**Два нетривиальных следствия, которые нужно использовать:**
- минимум потребляемой мощности, а значит максимум **продолжительности** полёта, —
  на малой скорости, близкой к висению (≈1–3 м/с для типичного мультиротора);
- максимум **дальности** (минимум энергии на единицу пути) — на заметно большей скорости
  (≈10–15 м/с).

Отсюда: «радиус действия» агента зависит от того, что оптимизируется. Это делает
задачу распределения содержательной, а не вырожденной.

Расход энергии:
```
E = ∫ P(v(t)) dt  +  N_takeoff·E_takeoff + N_land·E_land
```

### 3.3. Модель обнаружения (обязательно)

Вероятность обнаружения цели за один проход (модель бокового обзора / случайного поиска):
```
Pd_single = 1 − exp( − W · L / A_cell )
```
где `W` — **ширина полосы обнаружения** (зависит от высоты, разрешения камеры, контраста
цели), `L` — длина пройденного пути над ячейкой, `A_cell` — площадь ячейки.

Вероятность обнаружения за несколько проходов (накопление):
```
Pd_cumulative = 1 − Π_k (1 − Pd_k)
```

Простая параметризация `W` от высоты (для реалистичности):
```
GSD = altitude · pixel_pitch / focal_length         # разрешение на местности
W = W_max · f(GSD_target / GSD)   при GSD ≤ GSD_max, иначе 0
```
Модель намеренно простая, но она даёт главное: **связь между высотой, скоростью, полосой
перекрытия и вероятностью обнаружения.** Без неё «покрытие 100 %» не означает ничего.

### 3.4. Модель связи

Абстрактная, но с числами:
```
доставка сообщения (src→dst) возможна, если  ||p_src − p_dst|| ≤ R_comm
задержка  = базовая_задержка + дрожание + размер_сообщения / полоса   (накопление в очереди)
потеря    = вероятность_потери  (независимо на сообщение)
полоса    = байт_в_секунду  (ограничение очереди)
граф связи = G(t) по расстояниям → компоненты связности
```
Ключевое: `G(t)` может распасться на компоненты. Это и есть механизм, порождающий
главный эксперимент.

## 4. Цикл симуляции (псевдокод, детерминированный)

```python
def run(scenario, seed):
    rng = np.random.default_rng(seed)
    world, agents, tasks = build(scenario, rng)
    comms, faults, metrics = CommsBus(scenario), FaultManager(scenario), MetricsRecorder()

    # Фаза миссии: декомпозиция и первичное назначение
    tasks = scenario.mission_plugin.decompose(scenario.mission, world)
    alloc = allocator.allocate(world.snapshot(), tasks)
    assign_plans(agents, alloc, planner, validator)

    t = 0.0
    while t < scenario.t_end:
        # 1) инъекция и детекция отказов
        faults.inject_due(t)
        failed = faults.detect(world, agents)
        if failed: tasks = release_tasks_of(failed, tasks)

        # 2) доставка сообщений (с задержкой/потерями)
        comms.step(t, agents, world)

        # 3) глобальный распределитель — по событию, не каждый шаг
        if allocator.should_trigger(t, tasks, comms) and comms.gcs_reachable():
            alloc = allocator.allocate(world.snapshot(), tasks)
            update_plans_if_valid(agents, alloc, planner, validator)  # валидатор отвергает недопустимые

        # 4) локальный цикл агентов (следует за планом, локальный ремонт, безопасность)
        for a in agents:
            a.step(dt, neighbors=comms.neighbors_of(a), tasks=tasks)
            observe_and_update_belief(a, world, sensing)   # обнаружение целей

        # 5) события мира и метрики
        world.step(dt)
        metrics.record(t, world, agents, tasks, comms)

        assert no_collisions(world)          # жёсткое ограничение, а не метрика
        t += dt

    return metrics.finalize()
```

Требование детерминизма: `should_trigger` не должен зависеть от реального (настенного)
времени; только от модельного времени и событий. Иначе эксперименты невоспроизводимы.

## 5. Ключевые инженерные решения (и их обоснование)

| Решение | Выбор | Почему |
|---|---|---|
| Язык ядра | Python + numpy | скорость разработки важнее скорости исполнения на этом этапе |
| Оптимизатор распределения | OR-Tools (CP-SAT / маршрутизация) | не изобретать VRP-солвер; CP-SAT даёт оптимум для базового метода |
| Распределённое распределение | CBBA (своя реализация, ~300 строк) | ядро научного вклада, здесь писать своё оправдано |
| Связь | собственная абстрактная модель | существующее промежуточное ПО моделирует доставку, а не деградацию |
| Конфиги | pydantic + YAML | валидация сценариев и воспроизводимость |
| Хранение результатов | parquet/CSV + manifest | анализируемость, построение графиков |
| Промежуточное ПО | **без ROS2 на MVP** | ROS2 добавит сложности без пользы для исследовательских вопросов |
| Интеграция с PX4 | MAVSDK-Python | проще ROS2-моста, поддерживает несколько аппаратов, режим внешнего управления (offboard) |
| C++ | только по результатам профилирования | преждевременно |
| Графический интерфейс | не в MVP-0 | визуализация — производная от метрик, не наоборот |

### 5.1. Путь к PX4 (закладывать сейчас, делать позже)

1. `Agent` получает реализацию движения через интерфейс `MotionSource`.
2. `KinematicMotion` (симуляция) и `MavsdkMotion` (PX4) реализуют один интерфейс.
3. `MavsdkMotion` даёт: `goto_lla`, `set_velocity_body`, `get_state`, `arm/takeoff/land/rtl`.
4. Локальный слой безопасности/ремонта должен исполняться **на борту** — значит, на
   реальном железе это бортовой компьютер (Raspberry Pi / Jetson), а не наземная станция.
   Архитектурно это тот же Python-код, но развёрнутый на борту; `CommsBus` подменяется
   на реальный (Wi-Fi-сеть / XBee / 4G).
5. Ограничение, которое надо принять заранее: **режим внешнего управления (offboard) через
   MAVLink на 10–50 Гц не позволяет исполнять тактическое избегание**. Значит, на реальном
   борту либо бортовой компьютер делает всё локально и отдаёт PX4 только уставки, либо
   тактическое избегание переносится в PX4-модуль (C++). Это ключевое ограничение для
   раздела «SwarmCore Module» продуктовой части.

## 6. Антипаттерны (чего не делать)

1. **Начинать с визуализации.** Получите красивую анимацию, под которую потом будете
   подгонять алгоритм.
2. **Начинать с 3D и Gazebo.** Все исследовательские вопросы решаются в 2D.
3. **Писать собственный планировщик покрытия «с нуля» на первом шаге.** Сначала — сетка +
   «змейка» (lawnmower). Интеллект — в распределении, не в геометрии.
4. **Делать централизованный распределитель синхронным `for`-циклом на каждом шаге.**
   Это и нереалистично, и убивает производительность.
5. **Считать «столкновения» метрикой качества.** Это ограничение корректности.
6. **Оптимизировать метрики до того, как зафиксирован протокол эксперимента.**
   Сначала протокол, потом цифры (см. `03_experiment_program.md`).
7. **Пытаться сделать «универсальную декомпозицию миссий».** Домен — плагин.
8. **Симулировать физический уровень связи.** Достаточно абстрактной модели.
9. **Ставить ROS2 «потому что так делают все».** Обоснование — только конкретная
   потребность (например, готовая интеграция с Gazebo/PX4-мостом или сложная перцепция).
