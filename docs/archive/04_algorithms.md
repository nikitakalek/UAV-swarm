# Алгоритмы: обязательно / желательно / продвинутое

Правило отбора: включать алгоритм, только если он нужен для ответа на один из вопросов
из `03_experiment_program.md`. Всё остальное — отложить.

---

## 1. ОБЯЗАТЕЛЬНО (без этого MVP не существует)

### 1.1. Покрытие территории (планирование пути покрытия)
- **Что решает:** превратить область в набор исполнимых задач и маршрутов.
- **Минимум для MVP-0:** регулярная сетка + «змейка» (lawnmower/boustrophedon) внутри
  ячейки. ~100 строк.
- **Что изучить, если нужно дальше:** точная клеточная декомпозиция (Choset), декомпозиция
  на клетки, разложение BCD для непрямоугольных областей; обзор по БПЛА —
  [Cabreira et al., «Survey on Coverage Path Planning with UAVs», Drones 2019](https://www.mdpi.com/2504-446X/3/1/4).
- **Не изобретать:** сама «змейка» — тривиальна; интерес представляет разбиение области
  между агентами, а не форма полосы.

### 1.2. Распределение задач: аукцион/консенсус
- **CBBA — Consensus-Based Bundle Algorithm (алгоритм пакетов на основе консенсуса)** —
  центральный алгоритм проекта.
  [Choi, Brunet, How, IEEE T-RO 2009](https://ieeexplore.ieee.org/document/5173522).
  Даёт распределённое, без центра, назначение с построением «пакета» задач на агента —
  то есть решает именно вашу `ST-SR-TA` задачу, а не задачу назначения.
  **Важная тонкость:** гарантия «без конфликтов» обеспечивается при определённых
  допущениях о синхронности консенсуса; для асинхронного/разрывного случая нужны
  расширения. Это надо проверить и явно описать — тут ваша инженерная ценность.
- **Обзор альтернатив:** [«A Review of Multi-UAV Task Allocation Algorithms for a
  Search and Rescue Scenario», JSS 2024](https://www.mdpi.com/2224-2708/13/5/47) —
  хорошая стартовая точка для главы «обзор литературы».
- **Не изобретать:** не писать собственный консенсусный протокол с нуля. CBBA —
  300–500 строк, реализуется за неделю, проверен в литературе.

### 1.3. Оптимизация для базового метода (оракул)
- **OR-Tools** (Google): `CP-SAT` для точного оптимума на малых инстансах и
  `routing` для mTSP/VRP с ограничением по энергии.
  [OR-Tools](https://developers.google.com/optimization).
- **Зачем:** без оракула ваш базовый метод — соломенное чучело (см. S13 аудита).
- **Не изобретать:** MILP-солвер, VRP-эвристики, венгерский алгоритм (он решает
  вырожденный частный случай — см. S8).

### 1.4. Маршрутизация задач внутри агента (с учётом энергии)
- **Что решает:** в каком порядке агент обходит свои задачи, чтобы уложиться в энергию.
- **Минимум:** 2-opt / метод ближайшего соседа + проверка энергии с обязательным резервом 20 %.
- **Дальше:** маршрутизация в OR-Tools, LKH-3 для больших инстансов.

### 1.5. Модель энергии мультиротора
- **Формула:** Zeng, Xu, Zhang, «Energy Minimization for Wireless Communication with
  Rotary-Wing UAV», IEEE TWC 2019 (приведена в `02_mvp_architecture.md`).
- **Зачем:** без неё нет ни ограничения дальности, ни осмысленного распределения
  с учётом энергии.

### 1.6. Модель обнаружения / теория поиска
- **Koopman / Stone, «Theory of Optimal Search»** — классика:
  `Pd = 1 − exp(−W·v·t/A) = 1 − exp(−W·L/A)` (где `L` — длина пройденного пути),
  боковая кривая обнаружения, накопленная вероятность.
- **Зачем:** определяет целевую функцию миссии (см. S2 аудита). Это то, чего в исходной
  концепции нет вообще, и без чего защищать проект нельзя.

### 1.7. Валидатор плана и инварианты безопасности
- Не «алгоритм», а обязательный компонент: проверка геозон, энергии, сепарации,
  высотных коридоров. Дёшево и резко повышает инженерный уровень.

### 1.8. Метрики, воспроизводимость, статистика
- Детерминированный цикл, журнал событий, парные прогоны, доверительные интервалы
  бутстрепом, парный критерий Уилкоксона. Это «обязательный алгоритм» отчётности,
  а не разработки.

## 2. ЖЕЛАТЕЛЬНО (сильно усиливает проект)

### 2.1. Стратегическая деконфликтуация
- **Что решает:** гарантировать отсутствие столкновений *на уровне плана*, до полёта.
- **Методы:** эшелонирование по высоте, временные окна на ячейку, гарантия
  пространственной сепарации треков, приоритеты в пересечениях.
- **Почему это важнее тактического избегания:** это работает при любой частоте канала,
  проверяется формально и совпадает с реальной практикой BVLOS. Раздел `S5` аудита.

### 2.2. Инкрементальное/динамическое планирование пути
- **D\* Lite**, A\* с перепланированием — если появятся препятствия и бесполётные зоны.
- Для MVP-0 достаточно прямых сегментов: квадрокоптер почти голономный.

### 2.3. Консенсус для синхронизации состояния миссии
- **Что решает:** FR-8 (нет дублирования и потери задач после восстановления связи).
- **Методы:** распределённый консенсус на состоянии задач, векторные часы (vector clocks),
  идемпотентные операции над задачами.
- **Ценность:** редкая тема в студенческих проектах, и именно она делает «рой» роем,
  а не «парком с перераспределением».

### 2.4. Тактическое избегание столкновений
- **ORCA — взаимные препятствия по скорости (reciprocal velocity obstacles)**,
  [van den Berg et al. 2011](https://gamma-web.iacs.umd.edu/RVO2/),
  эталонная реализация [RVO2](https://github.com/snape/RVO2).
- **Требования:** ≥ 5 Гц обмен, задержка ≤ 200 мс, ограниченная динамика агентов.
- **Что обязательно сделать:** измерить, при какой задержке/частоте метод перестаёт
  гарантировать отсутствие конфликтов, и построить график «качество избегания vs
  задержка канала». **Это самостоятельный научный результат** и хороший ответ на
  вопрос «зачем вам вообще канал».
- **Не изобретать:** потенциальные поля как основной метод — устаревшая и плохо
  масштабируемая альтернатива; годятся только как простой базовый метод для сравнения.

### 2.5. Обнаружение отказов и логика деградации
- Детекция отказа по таймауту сигнала «жив» (heartbeat), детекция отрыва по расхождению
  предсказанного/фактического, деградация режимов (NORMAL / NO_GCS / DEGRADED / RTL).
- **Формализовать как конечный автомат** — это дёшево и очень наглядно.

### 2.6. Журнал объяснений решений
- Почему переназначили: какое событие, какие стоимости, какой распределитель, какое решение.
- Для акселератора и для доверия оператора это реальный дифференциатор
  по сравнению с «чёрным ящиком» платформы управления парком дронов.

## 3. ПРОДВИНУТОЕ / ИССЛЕДОВАТЕЛЬСКОЕ (только после MVP-3)

| Направление | Метод | Зачем | Риск |
|---|---|---|---|
| Планирование с учётом связи | планирование с учётом связности (connectivity-aware), сетевые графы, поддержание связности как ограничение | прямой ответ на «где граница централизации» на уровне плана, а не только архитектуры | высокий |
| Коалиционные задачи (`MR`) | CBBA с коалициями, гиперграфовое назначение | задачи, требующие нескольких БПЛА | высокий; комбинаторика |
| Вероятностное планирование поиска | POMDP, байесовские карты вероятности, информационные метрики (снижение энтропии) | математически корректная постановка поиска вместо суррогата покрытия | средний, но требует сильной матчасти |
| Обучение распределению | GNN для децентрализованного MRTA ([Tolstaya et al. 2020](https://arxiv.org/abs/2010.14009)), обучение по имитации MILP-оптимума | замена эвристик; путь к масштабируемости | высокий |
| RL для локального поведения | MARL (MAPPO/QMIX) для разрешения конфликтов и ремонта назначений | потенциально лучше ORCA в сложных сценах | очень высокий, требуется огромный бюджет симуляции |
| Формальные гарантии | функции барьера управления (CBF), MPC с ограничениями безопасности | сертифицируемая безопасность | средний/высокий |
| Распределённая оптимизация | DCOP, ADMM, распределённый MILP | теоретическая база децентрализации | высокий |
| Устойчивость и безопасность | подделка GPS, инъекции в MAVLink, византийские агенты | важная тема для реальных систем | средний |

### 3.1. Про ML — отдельно

Исходная идея «нейросеть предсказывает веса `w_distance`, `w_energy`, `w_time`, `w_risk`» —
**плохая цель для обучения**. Причины:
1. Веса функции стоимости **неидентифицируемы с точностью до масштаба**: умножение всех
   весов на константу не меняет решение. Обучение будет метаться по эквивалентным точкам.
2. Оптимальные веса зависят от сценария, но их легко подобрать обычным поиском по сетке
   или байесовской оптимизацией за несколько часов — нейросеть здесь не даёт выигрыша.
3. Нет датасета: чтобы обучить предсказание весов, нужны «правильные» веса, а они
   получаются только решением той же оптимизационной задачи офлайн — то есть вы
   обучаетесь предсказывать результат более дешёвого и точного метода.

**Где ML осмыслен:**
- предсказание **вероятности обнаружения** `Pd` по условиям (высота, скорость, время
  суток, тип подстилающей поверхности) — тут модель плохо выводится аналитически, а
  данные можно синтезировать или собрать;
- **GNN-политики назначения**, обученные имитацией решений CP-SAT — это активная
  научная линия, есть с чем сравниваться;
- предсказание **времени выполнения** задачи и вероятности отказа агента (прогностика
  для перераспределения).

То есть: ML применяется там, где **неизвестна модель**, а не там, где есть хороший
оптимизатор. Это и есть правильная формулировка «гибридного ИИ»: ML оценивает то, что
плохо моделируется, оптимизатор принимает решение.

## 4. Чего НЕ изобретать (готовое и проверенное)

| Не изобретать | Брать | Почему |
|---|---|---|
| VRP/MILP-солвер, венгерский алгоритм | OR-Tools (CP-SAT, маршрутизация) | годы разработки против дня интеграции |
| Консенсусное распределение задач | CBBA | проверен, воспроизводим, публикуем |
| Взаимное избегание столкновений | ORCA / RVO2 | формальные гарантии, эталонная реализация |
| Покрытие с декомпозицией | boustrophedon / BCD | классика, не требует исследований |
| Модель энергии | формула Zeng et al. | принята в литературе |
| Теория поиска | Koopman / Stone | корректная постановка вместо суррогата |
| Мультиагентная инфраструктура, наземная станция, формации | [Crazyswarm2](https://imrclab.github.io/crazyswarm2/index.html) (ROS2, в помещении, Crazyflie), [Aerostack2](https://aerostack2.github.io/), [MRS UAV System (CTU Prague)](https://mrs.fel.cvut.cz/system) | **это главный «велосипед» проекта**: инфраструктура мультидронных систем уже написана, открыта и поддерживается; изучать/переиспользовать, а не писать наземную станцию с нуля |
| Связь с PX4, мультиаппаратный режим внешнего управления (offboard) | MAVSDK-Python | проще и надёжнее собственного MAVLink-слоя |
| Отслеживание состояния | фильтр Калмана / EKF | не писать свой |

**Практический вывод по Crazyswarm2 / MRS / Aerostack2:** перед началом реализации
следует потратить 1–2 недели на изучение этих стеков и принять **осознанное** решение:
(а) строить симулятор на своём Python-ядре (быстрее для исследовательских задач,
полный контроль над экспериментом) или (б) обернуть готовый стек. Рекомендация для
вашего этапа — **(а) для исследовательского ядра + заимствование идей и, при переходе
на железо, переиспользование их решений по связи и позиционированию**. Это защищает
от вопроса «почему вы не взяли готовое».

## 5. Порядок освоения (что учить в каком порядке)

1. MRTA-таксономия (Gerkey & Matarić; Korsah et al.) — 1–2 дня, даёт язык описания.
2. Покрытие территории + модель обнаружения — 1 неделя.
3. Модель энергии + маршрутизация с ограничением дальности — 3–4 дня.
4. CBBA — 1–2 недели (разобрать статью и реализовать).
5. OR-Tools как оракул — 3 дня.
6. Модель канала связи и её влияние на координацию — 1 неделя.
7. ORCA и его границы применимости — 1–2 недели.
8. MAVSDK / PX4 SITL мультиаппаратный запуск — 2–3 недели.
9. ML (GNN/RL) — только после MVP-3 и только если есть ресурс.
