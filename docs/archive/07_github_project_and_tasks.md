# GitHub Projects и разбивка задач по модулям

Этот документ — как настроить доску на GitHub и какие задачи создать для трёх модулей
команды. Структура модулей (по 2 человека):

- **Модуль 1 — роевое управление:** распределение задач (CBBA, статический оракул,
  центральный аукцион), маршрутизация с энергией, валидатор плана, предотвращение
  столкновений, перераспределение.
- **Модуль 2 — симулятор:** среда (`World`), эмуляция движения дрона (кинематика),
  цикл симуляции, детерминизм, миссия/декомпозиция задач, испытательный стенд, CLI.
- **Модуль 3 — сенсоры:** радио (приёмник/передатчик → модель связи `CommsBus`),
  камера (модель обнаружения `Pd`), отказы (`FaultManager`).

---

## 0. Три вещи, которые надо решить ДО создания задач

### 0.1. Не начинайте Модуль 1 с CBBA и предотвращения столкновений

CBBA нужен на фазе P4, тактическое избегание столкновений (ORCA) — на P5/MVP-3.
Если Модуль 1 начнёт с «самого интересного», проект застрянет: без среды, сенсоров и
статического базового метода нечего распределять и не с чем сравнивать.

**Правильный порядок для Модуля 1:** статический оракул → валидатор плана → маршрутизация
с энергией → (P2) центральный аукцион → (P3) перераспределение → (P4) CBBA →
(P5) тактическое избегание.

### 0.2. У метрик и экспериментов нет владельца — это дыра

В разбиении «3 модуля × 2» никто не отвечает за метрики, матрицу прогонов и графики.
А именно они дают «цифры» для демо. **Рекомендация:** это отдельная «интеграционная»
дорожка, которую ведёт фаундер (см. 0.3), с помощью второго человека из любого модуля.

### 0.3. Фаундер в Модуле 1 — не должен быть бутылочным горлышком

Фаундер подключился к Модулю 1. Это нормально, но правило: **не владейте самым сложным
алгоритмом (CBBA) в одиночку**. Пусть напарник по модулю ведёт CBBA и глубокие алгоритмы,
а фаундер берёт: валидатор плана + перераспределение (интеграционную логику) + метрики.
Так фаундер остаётся доступным для координации команды.

## 1. Как настроить GitHub Projects (для новичка)

GitHub Projects — это канбан-доска. На ней «элементы» — это обычно issues. Элемент
перемещается по колонкам статуса: **Backlog → Todo → In Progress → In Review → Done**.

### Шаги настройки (15 минут)

1. В репозитории: вкладка **Projects** → **New project** → шаблон **Board**.
2. Назовите: `SwarmCore — P0/P1 спринт`.
3. Колонки — это поле **Status**. Добавьте статусы: `Backlog`, `Todo`, `In Progress`,
   `In Review`, `Done`.
4. Добавьте **кастомное поле** «Модуль» (single select): `Модуль 1`, `Модуль 2`,
   `Модуль 3`, `Интеграция`. (Кнопка «+» в шапке таблицы → «New field» → «Single select».)
5. Добавьте поле «Приоритет» (single select): `критично`, `нормально`, `можно позже`.
6. **Вехи (Milestones)** для фаз: в репозитории **Issues → Milestones → New milestone**.
   Создайте `P0`, `P1`, `P2`, `P3`, `P4`, `P5`. У вехи есть прогресс-бар — удобно видеть,
   сколько задач фазы закрыто.
7. **Метки (Labels)**: **Issues → Labels → New label**. Создайте:
   `module-1`, `module-2`, `module-3`, `integration`, `docs`, `bug`, `good-first-issue`.

### Как создавать задачи

Создавать issue можно двумя способами:
- прямо на доске: «Add item» → «+» → «Create new issue»;
- в **Issues → New issue**.

**Правило:** каждая задача привязана к **человеку** (assignee), а не к модулю. В модуле
два человека — назначение должно быть персональным.

### Поля, которые заполняете у каждого issue

| Поле | Что писать |
|---|---|
| Заголовок | что сделать (глагол + объект + результат) |
| Assignee | имя человека |
| Labels | `module-N` |
| Milestone | `P0`/`P1`/... |
| Поле «Модуль» | `Модуль N` |
| Поле «Приоритет» | `критично`/`нормально` |

## 2. Шаблон issue (вставляйте в тело каждой задачи)

```markdown
## Цель
Что и зачем делаем.

## Критерий готовности (definition of done)
- [ ] проверяемое условие 1
- [ ] проверяемое условие 2

## Интерфейсы
- сигнатура/контракт, если задача на стыке модулей

## Зависит от
- #номер_issue (если есть)

## Модуль / Фаза
Модуль 2 / P1
```

## 3. Что создавать ПРЯМО СЕЙЧАС (P0 + P1)

Правило: **создавайте issues только на текущий спринт** (P0 + P1 ≈ 2–3 недели).
Дальше — крупные вехи в бэклоге, а не 50 задач, в которых вы утонете.

### P0 — общая база (неделя 1)

| ID | Задача | Владелец |
|---|---|---|
| P0-1 | Прочитать `docs/00`–`06`, зафиксировать протокол разногласий | все |
| P0-2 | Заполнить таблицу имён (роли) и согласовать интерфейсы модулей письменно | фаундер |
| P0-3 | Закоммитить метрики и гипотезы (`03`) с датой | фаундер |
| P0-4 | Документ «что такое SwarmCore» (2 стр.) — контрольная точка P0 | фаундер |
| P0-5 | Настроить GitHub Projects (борд, поля, метки, вехи) | фаундер |

### P1 — MVP-0: статический рой + прогон с метриками (недели 2–3)

**Модуль 2 — симулятор (2 чел.)**

| ID | Задача | Критерий готовности |
|---|---|---|
| M2-1 | Каркас репозитория: `pyproject.toml`, пакет `swarmsim/`, `pytest`, минимальный CI | `pytest` зелёный; `pip install -e .` работает |
| M2-2 | `World`: границы, бесполётные зоны, цели, карта вероятности целей | заглушки `step(dt)`/`observe()` + тест на детерминизм сетки |
| M2-3 | `KinematicMotion`: движение к путевой точке со скоростью `v_c`, шаг `dt` | тест «агент достигает точку за ожидаемое время» |
| M2-4 | `SimLoop` + детерминизм: `run(scenario, seed)`, фиксированный ГПСЧ, manifest с хэшем | два прогона с одним зерном дают идентичные метрики |
| M2-5 | `MissionPlugin` (поиск): разбиение области на ячейки + «змейка» → `TaskSet` | для 1000×1000 м генерируется корректное число задач с полным покрытием |
| M2-6 | Испытательный стенд: прогон конфига (YAML) → CSV + manifest; CLI `run` | одна команда запускает прогон и выдаёт CSV |

**Модуль 3 — сенсоры (2 чел.)**

| ID | Задача | Критерий готовности |
|---|---|---|
| M3-1 | Модель обнаружения (камера): `Pd = 1 − exp(−W·L/A_cell)`, GSD от высоты, накопление | тест на монотонность `Pd` по длине пути и высоте |
| M3-2 | `CommsBus` (радио): доставка по дальности, задержка, потери, полоса; `send/broadcast` | тест «сообщение доставляется/теряется по заданной вероятности» |
| M3-3 | `FaultManager` (каркас): инъекция отказа агента и низкой батареи | тест «отказ в t=100 снимает агента с миссии» |

**Модуль 1 — алгоритмы (2 чел.)**

| ID | Задача | Критерий готовности |
|---|---|---|
| M1-1 | `static_voronoi`: диаграмма Вороного + выравнивание площадей (CVT/Ллойд) | секторы компактны, разброс площадей измерен; N = 5, 10, 20; проходит `PlanValidator` |
| M1-1a | `static_naive`: наивные полосы равной площади | 1 агент = 1 полоса; полнота без дублей; N = 5, 10, 20 |
| M1-2 | `static_oracle` (OR-Tools CP-SAT): офлайн-оптимум для малых N | назначение не хуже `static_naive` по `U(M)`; N≤10, M≤40 решается < 10 с |
| M1-3 | Маршрутизация внутри агента с энергией: порядок задач + ограничение `E ≤ e·(1−0.2)` + возврат домой | валидатор не пропускает маршрут с перерасходом |
| M1-4 | `PlanValidator`: геозоны, энергия, минимальная сепарация | недопустимый план отвергается |

**Интеграция (фаундер + помощник)**

| ID | Задача | Критерий готовности |
|---|---|---|
| INT-1 | `MetricsRecorder` + `run_matrix.py` + `plots.py` | первый график `T_detect(90 %)` vs `N` строится из CSV одной командой |

## 4. Бэклог (создавать ПОЗЖЕ, по одной фазе за раз)

Это крупные вехи в Milestones, а не десятки задач. Раскрываете их в issues, когда
дойдёте до фазы.

**P2 — централизованное распределение**
- M1: `central_greedy` (жадный аукцион) + пересчёт по событиям; сравнение с оракулом ≤ 10 %.
- M2: доработка стенда (события, конфиги), сценарии.
- M3: энергомодель от скорости (формула Zeng), доработка `CommsBus`.

**P3 — динамика и отказы**
- M1: триггеры перераспределения + локальный ремонт + конечный автомат режимов.
- M2: журнал событий; визуализация (в конце фазы).
- M3: полный `FaultManager` (отказ, разрыв связи, низкая батарея, новая цель).

**P4 — связь и децентрализация**
- M1: **CBBA** (фаза пакета + фаза консенсуса + тест «без конфликтов»).
- M3: разрывы сети, согласованность после восстановления (идемпотентность).
- M2: детерминизм при связи.

**P5 — сравнение архитектур**
- Интеграция/фаундер: матрица прогонов + статистика + графики + отчёт.
- Все: исправление найденных багов, доводка демо.

**Отдельно (не в MVP):** тактическое избегание столкновений (ORCA) — только после P4,
и только если стратегическая деконфликтуация (через `PlanValidator`) недостаточна.

## 5. Правила работы с доской

1. Задача двигается по статусам: **Backlog → Todo → In Progress → In Review → Done**.
2. `In Review` — кто-то из напарника/фаундера проверил критерий готовности.
3. Задача «висит» в `In Progress` больше одного синка без объяснения — флаг фаундеру.
4. Каждая задача — **одному человеку**. В модуле из двух человек — персонально.
5. Новая идея не добавляется в спринт без вопроса «ведёт ли это к северной звезде».
