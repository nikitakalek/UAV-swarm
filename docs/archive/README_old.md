# SwarmCore — техническая база проекта

SwarmCore — универсальная система координации роя БПЛА: оператор ставит миссию,
а система сама распределяет задачи между аппаратами, координирует их и продолжает
работу при отказах и потере связи.

Здесь два типа материалов:

1. **`docs/`** — техническая база проекта: аудит концепции, требования, архитектура,
   программа экспериментов, дорожная карта, правила работы команды.
2. **`swarmsim/`, `tests/`, `scripts/`** — код. Структура плоская: один модуль — один файл.

## Главный вывод аудита в одном абзаце

Исходная концепция методологически сильнее среднего студенческого проекта (сначала
контрольный метод, ML в конце, честная постановка гипотезы), но содержит три системных
дефекта, из-за которых её нельзя защищать в текущей формулировке: (1) отличие «роя» от
«парка дронов» описано через соломенное чучело — динамическое перераспределение задач уже
есть в коммерческих платформах управления парком дронов; (2) полностью отсутствует
**модель сенсора/обнаружения**, поэтому миссия «найти цели» математически не определена,
а метрика «покрытие, %» подменяет цель средством; (3) отсутствует **модель связи как
ограничения первого класса**, а именно она — а не алгоритм распределения задач —
определяет, где проходит граница между централизацией и децентрализацией. Исправление
этих трёх пунктов переводит проект из «мы написали диспетчер с анимацией» в «мы измерили,
при каких условиях централизация перестаёт быть выгодной».

## Порядок работы

1. Прочитать `00_concept_audit.md`, согласиться/поспорить с каждым пунктом.
2. Зафиксировать определение и требования (`01`).
3. Согласовать MVP и архитектуру (`02`).
4. Зафиксировать программу экспериментов (`03`) **до** написания кода — иначе метрики
   будут подогнаны под то, что получилось.
5. Только после этого — реализация по дорожной карте (`05_roadmap.md`).

## Создание задач в GitHub

Все задачи (P0–P6, 42 штуки) лежат в скрипте `scripts/create_issues.sh`. Он создаёт
метки, вехи и issues в GitHub, пропуская уже существующие (можно запускать повторно).

```bash
brew install gh && gh auth login     # один раз
./scripts/create_issues.sh           # из корня репозитория
DRY_RUN=1 ./scripts/create_issues.sh # только показать, ничего не создавать
```

Начинать работу следует с вех **P0 и P1** — остальные задачи уже лежат в Backlog.

## Журнал правок (ревизия 2)

- Исправлена формула поиска Купмана (была размерно некорректна): `1 − exp(−W·v·t/A)`.
- Уточнено утверждение про энергию: минимум мощности (максимум продолжительности полёта)
  достигается на малой скорости вблизи висения, а не строго при `v → 0`.
- Исправлена арифметика полного факторного плана (4320 → 4608) и устранены расхождения
  «5 архитектур / 6 контрольных методов» и «графики 1–5 / 1–6».
- Добавлены: требования по кибербезопасности (MAVLink без шифрования), синхронизация
  времени между бортами, примечание по регуляторике полётов в РФ.
- Все англицизмы (baseline, fleet, harness, gate, seed, ablation, crossover и др.)
  переведены на русский; при первом упоминании ключевого термина оставлено английское
  написание в скобках для поиска по литературе.
