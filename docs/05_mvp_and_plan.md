# MVP и план на двоих

## 1. Что такое MVP к 20 ноября

**Цель демонстрации:** показать, что «модуль на плате» реально управляет группой
аппаратов на настоящем автопилоте, а не рисует анимацию.

**Сценарий демо (≈ 2 минуты видео):**
1. Оператор одной командой задаёт участок (многоугольник) группе из 3 аппаратов.
2. Модуль делит участок на 3 компактных сектора, аппараты взлетают на разных высотах
   и обследуют свои секторы «змейкой».
3. Аппарат №2 «отказывает» (принудительная посадка/отключение).
4. Модули замечают потерю, неотработанная часть сектора №2 делится между №1 и №3.
5. Все аппараты завершают работу и возвращаются. На экране — карта и лог событий.

**Стенд:**

```
 MacBook M1                                   Raspberry Pi 4B («модуль»)
 ┌──────────────────────────┐   Wi-Fi/UDP    ┌───────────────────────────────┐
 │ PX4 SITL × 3 аппарата    │◄──────────────►│ swarm_node --id 1  (MAVSDK)   │
 │ (программная модель      │   MAVLink      │ swarm_node --id 2             │
 │  автопилота PX4)         │                │ swarm_node --id 3             │
 │ QGroundControl — карта   │                │  ↕ обмен состоянием по UDP    │
 └──────────────────────────┘                └───────────────────────────────┘
```

Каждый `swarm_node` — отдельный процесс, который «сидит» на своём аппарате и общается
с соседями только через сеть. Так мы честно эмулируем «по плате на борт», имея одну плату.

**Честные упрощения MVP (говорим о них на защите сами):**
- распределение делает узел-лидер (минимальный id), остальные — запасные; полная
  децентрализация — в v1;
- разведение аппаратов — стратегическое (свои секторы + разные высоты), без тактического
  уклонения;
- связь «борт–борт» — Wi-Fi, без модели помех;
- полёт виртуальный (SITL), реальные аппараты — следующий этап.

**Что переиспользуем из готового кода:** `swarmsim/sectors.py` (деление участка),
`swarmsim/alloc.py` (`CentralGreedyAllocator.reassign` — перераспределение после отказа),
`swarmsim/plan.py` (маршрут и валидатор плана). Новое — только узел `swarm_node`,
обмен сообщениями и связка с MAVSDK.

## 2. Критерии готовности MVP

- [ ] 3 аппарата PX4 SITL запускаются одной командой.
- [ ] Узлы на Raspberry Pi подключаются к своим аппаратам, видят друг друга.
- [ ] Участок делится и облетается; разнос по высоте ≥ 3 м, секторы не пересекаются
      (проверка валидатором).
- [ ] При отказе одного аппарата оставшиеся задачи перераспределены за ≤ 5 с,
      ни одна задача не потеряна и не продублирована (проверка по логу).
- [ ] Видео + лог + одна картинка «до/после отказа» для заявки.

## 3. Роли на MVP

| | Участник А (ты) | Участник Б |
|---|---|---|
| Зона | логика узла: деление участка, перераспределение, протокол обмена, валидатор; координация; заявка и питч | стенд: PX4 SITL ×3, MAVSDK, Raspberry Pi, сеть, запуск одной командой, запись видео |
| Общее | интервью с клиентами — делим список пополам | |

Правило: у каждой задачи один владелец; интерфейс между зонами — команды узла
к аппарату (`arm`, `takeoff`, `goto`, `land`, `get_state`) — фиксируем в первую неделю.

## 4. План по неделям (до подачи 20 ноября)

Режимы нагрузки на день: **минимум** 15–20 мин, **норма** 45–90 мин, **длинный** 2–4 ч
(выходные). Пропущенный день не компенсируем двойной нагрузкой — сдвигаем хвост.

| Неделя | Участник А | Участник Б | Контрольная точка (воскресенье) |
|---|---|---|---|
| **1** (27.10–02.11) | интерфейс узел↔аппарат; заготовка `swarm_node` на заглушке аппарата (без PX4); список 20 компаний для интервью | PX4 SITL ×3 на Mac; MAVSDK-скрипт «взлёт-точка-посадка» для 3 аппаратов. **Если SITL на M1 не заводится за 1 вечер — сразу Linux-ВМ/Docker, не бороться** | 3 виртуальных аппарата взлетают по скрипту |
| **2** (03.11–09.11) | деление участка + маршруты «змейкой» в `swarm_node`; обмен состоянием по UDP | перенос узлов на Raspberry Pi, связь Pi↔Mac по Wi-Fi, запуск всего одной командой | группа облетает участок, узлы на Pi |
| **3** (10.11–16.11) | отказ и перераспределение; лог событий; 3–5 интервью | сценарий отказа, запись видео, картинка для заявки; 3–5 интервью | видео демо готово |
| **4** (17.11–20.11) | заявка + one-pager на основе [00_summary.md](00_summary.md); итоги интервью в документы | вычитка, резерв на исправления | **заявка подана** |

**Если к концу недели 2 стенд не работает** — режем демо до 2 аппаратов и отказа без
перераспределения части сектора (весь сектор целиком). Заявку подаём в любом случае.

## 5. После подачи: план на полгода (ориентировочно)

| Период | Продукт | Клиенты | Итог периода |
|---|---|---|---|
| 21.11 – 31.12 | разбор демо, стабилизация кода | **10–15 интервью**, выбор первого сегмента | решение: агро или съёмка; 1–2 тёплых контакта у производителей |
| январь (сессия) | минимум: поддержка, ничего нового | 2–3 интервью | — |
| февраль – март | v0.2: работа без наземной станции (децентрализованное распределение), учёт заряда; переход на 2 реальных небольших аппарата PX4 в помещении | повторные встречи, обсуждение пилота | первый реальный полёт пары аппаратов |
| апрель – май | v0.3: выбор mesh-радиомодуля, первая плата-носитель (макет) | предложение пилота производителю; заявка на грант | письмо о намерениях / договор пилота |

**Принцип:** каждый следующий технический шаг — только после того, как интервью
подтвердили, что он нужен клиенту. Если гипотезы V1/V3 из [01](01_problem_and_customer.md)
не подтверждаются — останавливаемся и меняем сегмент, а не дописываем функции.
