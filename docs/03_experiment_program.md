# Программа экспериментов

Это главный документ проекта. Он фиксируется **до** реализации алгоритмов.
Если менять метрики после получения результатов — эксперимент перестаёт быть
доказательством.

---

## 1. Гипотезы

Каждая гипотеза должна быть опровергаемой. Формулируем так, чтобы **любой** исход был
результатом.

| ID | Гипотеза | Основная метрика | Ожидание (до эксперимента) |
|---|---|---|---|
| H1 | Централизованная архитектура превосходит децентрализованную (CBBA) по качеству назначения в номинальных условиях | `U(M)` — целевая функция миссии | да, но разрыв ≤ 5 % → тогда децентрализация «почти бесплатна» |
| H2 | При деградации связи децентрализованная архитектура превосходит централизованную | доля выполненных задач, `U(M)` при потерях ≥ 30 % и разрывах связи с наземной станцией (GCS) | да |
| H3 | Существует точка перехода по N: начиная с некоторого `N*` централизованное планирование теряет преимущество | `U(M)` и `T_compute` как функции N | `N*` в диапазоне 10–30 |
| H4 | Перераспределение восстанавливает миссию при отказах до 30 % агентов | `P(mission complete)`, `T_recovery` | да, при наличии избыточной ёмкости |
| H5 | Статический оракул (базовый метод) лучше роя в номинальном режиме и хуже при нарушениях | `U(M)` в 3 режимах | да — и это **нужно показать честно** |
| H6 | Тактическое избегание конфликтов не даёт выигрыша, если стратегическая деконфликтуация корректна | число опасных сближений, накладные расходы по времени | скорее нет выигрыша → упрощение системы |
| H7 | ML поверх оптимизатора даёт выигрыш только на неоднородных/шумных задачах | `U(M)` при равном бюджете настройки | почти наверняка нет выигрыша в MVP-сценариях |

H6 и H7 сформулированы как **гипотезы отсутствия эффекта** специально: отрицательный
результат — это экономия месяцев работы, и его нужно уметь получить и признать.

## 2. Сравниваемые архитектуры (контрольные и рабочие методы)

| Обозн. | Название | Что делает | Роль |
|---|---|---|---|
| **B0** | `static_oracle` | офлайн-разбиение, вычисленное оптимизатором с полным знанием мира (в т.ч. распределения целей); без перераспределения | **честный** ориентир сверху/снизу |
| **B1** | `static_roundrobin` | равные сектора по числу агентов (циклическое разбиение), без динамики | «наивный» контроль (для контраста) |
| **B2** | `central_greedy` | центральный жадный аукцион с пулом задач, пересчёт по событиям | рабочая централизованная архитектура |
| **B3** | `central_optimal` | CP-SAT/MILP, оптимум для малых N (≤ 12 агентов, ≤ 40 задач) | эталон качества |
| **B4** | `cbba` | распределённый аукцион, без центра, с консенсусом | децентрализованная архитектура |
| **B5** | `hybrid` | B2 при наличии наземной станции + локальный ремонт агентами при потере связи | ваша рабочая гипотеза |

**Обязательное правило честности:** B1 (циклическое разбиение) нельзя использовать как
основной базовый метод для доказательства пользы роя. Он слабый, и его разгром ничего не
доказывает. Основной ориентир — **B0** (оракул со статическим разбиением). Рой обязан
побеждать B0 **только в режимах с нарушениями**, и это надо артикулировать в презентации
прямым текстом.

## 3. Независимые переменные (факторный план)

| Фактор | Обозн. | Уровни | Зачем |
|---|---|---|---|
| Число агентов | `N` | 5, 10, 20, 50 | масштабируемость, точка перехода H3 |
| Число целей | `M` | 10, 50, 200 | нагрузка на распределение |
| Неоднородность плотности целей | `κ` | однородная / кластеризованная (2–3 кластера) | где централизация выигрывает |
| Интенсивность отказов | `λ` | 0, 0.1, 0.2, 0.3 (доля агентов за миссию) | H4 |
| Качество канала | `q` | идеальный / задержка 200 мс + потери 10 % / потери 30 % / разрыв связи с наземной станцией 30 % времени | H2 |
| Нестационарность | `D` | 0 / новые цели на 1/3 и 2/3 времени миссии | H1, режим 3 |
| Размер области | `A` | 500×500, 1000×1000, 2000×2000 м | базовая физика покрытия |
| Тип миссии (подключаемый модуль) | `P` | поиск (полнофакторно), инспекция (проверка переносимости ядра) | FR-1 |

**Полный факторный план не нужен** — он взорвётся: перебор всех 8 факторов даёт
`4·3·2·4·4·2·3·2` = **4608 конфигураций**. Использовать **последовательное планирование**:
1. Базовая линия: `A=1000×1000`, `κ` однородная, `λ=0`, `q` идеальный, `D=0`,
   варьируется только `N`. → 4 конфигурации × 5 методов (B0, B1, B2, B4, B5) × 20 зёрен
   (seed); B3 (точный оптимум) добавляется только при N ≤ 10.
2. Вокруг базовой линии — меняем **один фактор за раз** (one-factor-at-a-time).
3. Только для обнаруженных интересных областей — полный факторный поднабор.

Зёрна (seed): **не менее 20 на конфигурацию** (для оценки доверительных интервалов и
парного сравнения). Для дешёвых конфигураций — 50.

**Парный дизайн (обязательно):** все архитектуры прогоняются на **одном и том же мире**
(то же зерно → те же позиции целей, та же последовательность отказов). Это убирает
дисперсию мира и делает сравнение чувствительным. Без этого вы будете измерять шум.

## 4. Метрики: точные определения

| Метрика | Обозн. | Определение | Тип |
|---|---|---|---|
| Время до обнаружения X % целей | `T_detect(X)` | модельное время, когда накопленная `Pd`-взвешенная доля обнаруженных целей ≥ X | основная (поиск) |
| Целевая функция миссии | `U(M)` | `Σ_j priority_j·1[выполнено вовремя] − λ_E·Σ E_i − λ_T·makespan` (общее время миссии) | основная (обобщённая) |
| Доля выполненных задач | `CR` | `выполненные / всего` | основная |
| Средняя задержка | `T_latency` | mean `(t_fact − t_plan)` по задачам | диагностика |
| Энергия | `E_total` | суммарная потреблённая энергия, Вт·ч | основная |
| Эффективность покрытия | `CE` | покрытая площадь / потреблённая энергия | диагностика |
| Время перераспределения | `T_realloc` | от события до валидного нового назначения | основная |
| Время восстановления | `T_recovery` | от отказа до момента, когда задачи отказавшего перераспределены и исполняются | основная |
| Трафик | `B` | суммарные байты / (N · T_mission), байт/с на агента | основная |
| Число сообщений | `N_msg` | по типам (состояние, намерение, задача, событие) | диагностика |
| Число конфликтов | `N_conf` | срабатывания тактического разрешения | диагностика |
| **Опасные сближения** | `N_nm` | пары, расстояние < 2× минимума сепарации | диагностика |
| **Столкновения** | `N_col` | пары, расстояние < min_separation | **жёсткое ограничение = 0** |
| Автономность без наземной станции | `A_gcs` | доля задач, выполненных в интервале потери связи | основная (H2) |
| Дублирование задач | `N_dup` | задач, выполненных более одного раза | **жёсткое ограничение = 0** |
| Потерянные задачи | `N_lost` | задач, «повисших» после восстановления связи | **жёсткое ограничение = 0** |
| Вычислительная нагрузка | `CPU` | реальное (настенное) время на шаг, мс; и на перераспределение | основная (H3) |
| Масштабируемость | — | `U`, `T_compute`, `B` как функции N | основная (H3) |

Жёсткие ограничения (`N_col`, `N_dup`, `N_lost`) — **не метрики, а условия корректности**.
Прогон, нарушивший их, помечается `invalid` и в статистику качества не попадает
(но попадает в отчёт отдельной строкой — это важный факт, а не то, что можно спрятать).

## 5. Что именно доказывает пользу роевого подхода

Ключевая идея дизайна: **эффект должен возникать от нарушения, а не от наличия роя.**

| Утверждение | Как доказывается |
|---|---|
| Рой устойчивее к отказам | `P(mission complete)` при `λ` от 0 до 0.3: B0/B1 падают, B2/B4/B5 держатся |
| Рой устойчивее к деградации связи | `A_gcs` и `U(M)` при `q` от идеального до разрыва: B2 падает, B4/B5 держатся |
| Есть точка перехода по масштабу | `U(N)` и `T_compute(N)`: кривые B2 и B4 пересекаются в `N*` |
| Локальная автономия полезна | исследование методом исключения (ablation): B5 с локальным ремонтом и без — разница в `T_recovery`, `CR` |
| Перераспределение полезно | метод исключения: B1 (нет перераспределения) vs B2 (есть) при одинаковом первичном назначении |
| Модель обнаружения важна | метод исключения: планирование по «покрытию, %» vs по ожидаемому `Pd` — разница в `T_detect(90 %)` |

Последний метод исключения — самый «научный» и самый убедительный: он показывает, что
**планирование по ожидаемой вероятности обнаружения лучше планирования по покрытию**.
Это нетривиальный результат, который можно докладывать.

## 6. Главные графики отчёта

1. **Пересечение кривых (crossover) по масштабу:** `U(M)` (нормированная к B0) vs `N`
   для B0/B2/B4/B5. Точка пересечения — центральный результат.
2. **Кривая устойчивости:** `P(mission complete)` vs доля отказавших агентов, 5 кривых.
3. **Кривая деградации связи:** `U(M)` vs потери (0 → 40 %) и отдельно режим разрыва
   связи с наземной станцией.
4. **Фронт Парето:** качество (`U`) vs трафик (`B`) vs вычисления (`T_compute`) — точки
   соответствуют архитектурам. Это самый «взрослый» график: он показывает, что выбор
   архитектуры — это компромисс, а не «одна лучше всех».
5. **Диаграмма метода исключения:** вклад каждого модуля (перераспределение, локальный
   ремонт, Pd-планирование, тактическое избегание) в `U`.
6. **Карта миссии:** траектории + места отказов + интервалы потери связи — для демо.

## 7. Статистика и отчётность

- Парные прогоны → **парный критерий Уилкоксона (paired Wilcoxon signed-rank)** для
  попарных сравнений архитектур (непараметрический, не требует нормальности).
- Доверительные интервалы — **бутстреп (bootstrap)**, 1000 ресемплов, т.к. распределения
  времени — не нормальные.
- Обязательно указывать **величину эффекта (effect size)**, а не только p-value:
  «разрыв 3 % при дисперсии 12 %» — это отсутствие эффекта, даже если p < 0.05.
- Отчёт по каждой конфигурации: `mean ± CI95`, `median`, `IQR`, число невалидных прогонов.
- Все прогоны сохраняются; в отчёт идут ссылки на артефакты (parquet + manifest).

## 8. Правила против самообмана

1. **Одинаковый мир для всех архитектур** (парный дизайн по зерну).
2. **Одинаковая информация:** ни один распределитель не получает больше данных, чем другие.
   Если B2 знает глобальное состояние, а B4 — нет, это разные условия, и сравнивать их
   нельзя без оговорки. В отчёте — явная таблица «что знает каждая архитектура».
3. **Одинаковый бюджет настройки.** Нельзя тюнить параметры роя месяц, а базовый метод
   запускать с дефолтными.
4. **Никакой выборочной подачи результатов (cherry-picking).** Число зёрен фиксируется
   заранее; неудачные прогоны не выбрасываются из статистики (кроме невалидных по
   жёстким ограничениям, и их число указывается).
5. **Метрики фиксируются до эксперимента** (этот документ — коммит в репозиторий
   с датой; изменение метрик после — отдельный коммит с обоснованием).
6. **Публиковать отрицательные результаты.** «Централизованное планирование не хуже»
   или «тактическое избегание не нужно» — это результат, а не провал.

## 9. Критерии остановки (когда честно остановиться)

Фиксируем заранее условия, при которых нужно менять направление, а не «дожимать» идею:

| Условие | Что это значит | Действие |
|---|---|---|
| B4 (CBBA) в пределах 5 % от B2 (централизованный) при `q` идеальном и `N ≤ 20` | централизация не даёт качества | переформулировать вклад: строить систему сразу децентрализованной, а центр оставить только для оператора и мониторинга |
| `T_realloc > 10 с` при `N=20` | перераспределение не успевает за обстановкой | уменьшить размер задач (мельче гранулярность), иначе режим 3 (нестационарность) не работает |
| Выигрыш `T_detect` от N выходит на плато при `N ≤ 10` для `A = 1000×1000` | площадь мала для роя | увеличить масштаб сценария или признать, что рой нужен только для больших территорий |
| Столкновения не удаётся свести к 0 без разведения по высоте | тактическое избегание в модели не работает | зафиксировать эшелонирование как штатный механизм и честно описать ограничение |
| ML не даёт выигрыша при равном бюджете настройки на 3 и более сценариях | ML не нужен | исключить ML из проекта, сосредоточиться на распределённых алгоритмах и отказоустойчивости |

Наличие раздела «критерии остановки» само по себе сильно повышает доверие к проекту:
он показывает, что команда не защищает идею, а исследует её.
